## 10.1 Aufgaben der Transportschicht

Zuverlässige Ende-zu-Ende-Datenübertragung, auch bei unzuverlässiger (nicht beeinflussbarer) Vermittlungsschicht eines Netzbetreibers.

![[10-tsap-nsap-tpdu.jpeg]]

Die Transportinstanzen der Endsysteme tauschen TPDUs (Transport Protocol Data Units) aus. Sie greifen nach oben über den TSAP (Transport Service Access Point) und nach unten über den NSAP (Network Service Access Point) zu. Zwischenknoten betreiben nur die Schichten 1 bis 3.

- Fehlerbehandlung (Ende-zu-Ende im Gegensatz zu Schicht 2)
- Aushandlung von Dienstgüte-Eigenschaften
- Flusskontrolle (ebenfalls Ende-zu-Ende)

## 10.2 Schnittstellenereignistypen: Primitive des Dienstes

Ein Bezeichner besteht aus:

- **Dienstname**, z.B. Sicherung (Link, L), Netzwerk (Network, N), Transport (Transport, T), Darstellung (Presentation, P)
- **Dienstprimitivname**, z.B. ConnectionEstablishment (Con), Data Transfer (Dat), ConnectionRelease (Dis oder Rel), ConnectionReset (Res), ConnectionAbort (Abo)
- **Grundform der Dienstleistung:** Anforderung (Request, Req), Anzeige (Indication, Ind), Antwort (Response, Rsp), Bestätigung (Confirmation, Cnf)

**Beispiel:** "Verbindungsaufbau-Anforderung eines Transportdienstes": `T ConReq`

## 10.3 Transportdienst

![[10-transportdienst-ablauf.jpeg]]

**Verbindungsorientiert** (Realisierung durch TCP, Transmission Control Protocol): `TConReq` ⇒ `TConInd`, `TConRsp` ⇒ `TConCnf`, danach `TDatReq` ⇒ `TDatInd` (auch `TExpDatReq` ⇒ `TExpDatInd` für Expressdaten) und zum Schluss `TDisReq` ⇒ `TDisInd`.

**Verbindungslos** (Realisierung durch UDP, User Datagram Protocol): nur `TDatReq` ⇒ `TDatInd`, ohne Verbindungsauf- und -abbau.

**Zustandsmodell für den Transportdienst:**

![[10-zustandsmodell-transportdienst.jpeg]]

| Zustand | Übergang | Folgezustand |
| --- | --- | --- |
| Ruhe | `TConReq`, `TConInd` | Verbindung im Aufbau |
| Verbindung im Aufbau | `TConRsp`, `TConCnf` | Verbindung aufgebaut |
| Verbindung im Aufbau | `TDisReq`, `TDisInd` | Ruhe |
| Verbindung aufgebaut | `TDatReq`, `TDatInd` oder `TExpDatReq`, `TExpDatInd` | Verbindung aufgebaut |
| Verbindung aufgebaut | `TDisReq`, `TDisInd` | Ruhe |

## 10.4 Gesicherter Verbindungsabbau

**Problem:** Disconnect Request (DR), während noch Daten unterwegs sind. Lösung: quittierter Abbau (automatisches Disconnect Confirm, DC).

![[10-verbindungsabbau-dc-verloren.jpeg]]

Jedoch: Die Quittung (DC) kann verlorengehen. B ist dann unsicher, ob A wirklich abbaut. Lösung: **Dreiwege-Quittungsverfahren** (DR, DC, AC):

![[10-dreiwege-quittung.jpeg]]

Nun könnte die zweite Quittung (AC) verlorengehen. Es erfolgt jedoch keine weitere Quittierung, sondern lediglich eine zusätzliche Timer-Überwachung.

> **Merke:** Der "Three-Way-Handshake" wird z.B. bei TCP auch beim Verbindungsaufbau eingesetzt.

## 10.5 Aushandlung von Dienstgüte-Eigenschaften

Wesentliche Dienstgüte-Eigenschaften (QoS, Quality of Service):

1. Datenrate [MBit/s] oder Durchsatz [MByte/s]
2. Paketfehlerrate, bspw. $10^{-11}$
3. Verbindungsaufbauzeit, bspw. $T = 10$ ms bei LTE oder $T = 1$ ms bei 5G
4. Wahrscheinlichkeit für Transferfehler, bspw. $10^{-12}$
5. Prioritäten bei der Übertragung, bspw. TVoP: hoch, VoIP: mittel, E-Mail oder SMS: niedrig
6. Wahrscheinlichkeit für Verbindungsausfall, bspw. $10^{-5}$
7. Verbindungsabbauverzögerung, bspw. $T = 15$ ms

**Beispiel der Optionsabsprache bezüglich QoS:**

![[10-qos-optionsabsprache.jpeg]]

Der Initiator fordert mit `TConReq` einen Transferdurchsatz TP = 8 Mbit/s an. Der Partner antwortet mit `TConRsp` und bietet nur TP = 5 Mbit/s an. Das `TConCnf` bestätigt den ausgehandelten Wert von 5 Mbit/s.

## 10.6 Transportprotokolle im Internet: TCP und UDP

**TCP (Transmission Control Protocol):**

- Beliebige Nachrichtenlänge, als Pakete von max. 64 kByte übertragen
- Reihenfolgegarantie, 32-Bit-Folgenummern
- Verbindungsauf-/abbau mit Dreiwege-Quittungsverfahren
- Fensterbasierte Flusskontrolle
- Fehlerbehandlung durch erweitertes Prüfsummenverfahren (in Software)

**TCP-Struktur** (einheitlich für alle Nachrichtentypen):

| Feld | Länge / Bedeutung |
| --- | --- |
| Quell-Port | 16 Bit |
| Ziel-Port | 16 Bit |
| Sequenznummer | 32 Bit |
| Piggyback Acknowledgment | 32 Bit |
| TCP Header Length, Steuerbits | |
| Fenstergröße | 16 Bit, variabel |
| Prüfsumme | |
| Urgent Pointer | relativer Bezug zu wichtiger Folgenummer |
| Optionsfeld | z.B. Aushandeln der Puffergröße |
| Daten | |

**UDP (User Datagram Protocol):** verbindungslos, reine IP-Schnittstelle, einfacher Header (Adressen, Länge, Prüfsumme, Daten)

## 10.7 Adressierung

**TSAP (Transport Service Access Point):** Socket mit Portnummer bei TCP; entspricht der Prozesszugangsadresse (inkl. NSAP), z.B. `129.13.4.10 [1117]`. Die Portnummern werden über einen Nameserver ermittelt:

![[10-ports-nameserver.jpeg]]

1. Der Benutzer (Port 1117) fragt den Nameserver unter dem bekannten Port 53.
2. Danach verbindet er sich mit dem Anwendungsserver unter dem nicht netzweit bekannten Port 1333.

Bezeichnung bei TCP und UDP: **Port** (16 Bit, Portnummern von 0 bis 65535). Die Ports 0-1023 sind fest reserviert ("well-known"), z.B. Port 53 für DNS, Port 80 für HTTP.

## 10.9 Flusskontrolle: Schiebefensterprotokolle

**Idee:** Mehr als 1 Paket ist unterwegs, bis die Quittung eintrifft, zur Effizienzsteigerung (die Laufzeit ist hoch).

- Umfangreichere Laufnummern, verwaltet durch das Schiebefenster des **Senders**
- Fenstergröße $F$ (Anzahl unbestätigter Pakete), mit $F = 1$ bei Stop-and-Wait: Laufnummern $0 \ldots F$ (um Eindeutigkeit zu erreichen)

![[10-stop-and-wait.jpeg]]

Bei $F = 3$ gelten die Laufnummern $0 \ldots 3$ ⇒ Pipeline-Verarbeitung:

![[10-schiebefenster-f3.jpeg]]

## 10.10 Fehlerbehandlung bei Schiebefensterprotokollen

**Go-back-n** ($F = 5$): Fehlerhafte Pakete werden vom Empfänger ignoriert (nicht bestätigt), ebenso alle nachfolgenden Pakete. Der Sender wiederholt alle diese Pakete. Das ist ungünstig bei hoher Fehlerrate.

![[10-go-back-n.jpeg]]

**Selective Repeat** ($F = 5$): Nur fehlerhafte Pakete werden erneut gesendet, nachfolgende korrekte Pakete werden zuvor gepuffert. Quittiert wird mit einer Sammelquittung. Das ist ein Kompromiss zwischen Nachrichten- und Pufferaufwand (beim Empfänger), dafür bleibt die Reihenfolgetreue erhalten.

![[10-selective-repeat.jpeg]]

## 10.11 Adaptive Flusskontrolle bei TCP

- Festlegung einer maximalen Fenstergröße sowie eines Schwellwerts unterhalb dieses Maximums
- Beginn mit Fenstergröße 1 ("Slow Start"), exponentielle Erhöhung bis zum Schwellwert bei erfolgreich bestätigten Nachrichten, lineare Erhöhung nach Überschreiten des Schwellwerts bis zum Maximum
- Zurücksetzen der Fenstergröße auf einen geringen Wert bei Ablauf eines Timeouts (z.B. bei Paketverlust), während auf eine Quittung gewartet wird

![[10-tcp-slow-start.jpeg]]

## 10.12 TCP/IP-Programmierung: Sockets

**Basis:** Sockets als Dienstzugangspunkt ⇒ TSAP

![[10-socket-aufrufe.jpeg]]

| Client-Prozess A | Server-Prozess B |
| --- | --- |
| `socket()` ⇒ Socket | `socket()` ⇒ Socket |
| | `bind(Socket, Name)`: Benenne Socket |
| | `listen(Socket)`: Erzeuge Pufferplatz |
| `connect(Socket, Prozess B)` | `accept(Socket)`: Warte auf Verbindungsanforderung |
| `send(Socket, data)` | `receive(Socket, data)` |
| `receive(Socket, data)` | `send(Socket, data)` |
| `close(Socket)` | |

- APIs in mehreren Programmiersprachen (Ursprünge in C)
- **Stream Sockets:** Realisierung auf Basis von TCP für Datenströme
- **Datagram Sockets:** UDP-basiert, einfache Datagramme ⇒ kein Verbindungsaufbau; Funktionen: `sendto()`, `recvfrom()`
- Zusätzlich: "Select" zum Warten an mehreren Sockets

**Java Sockets: Beispiel für die Server-Seite**

```java
ServerSocket serverSocket = new ServerSocket(port); // generiere neuen Socket mit bestimmter Portnummer
while (true) {
    Socket clientSocket = serverSocket.accept();     // warte auf Nachrichten
    InputStream input = clientSocket.getInputStream(); // Datenstrom empfangen
    int data = input.read();                         // Daten auslesen
    clientSocket.close();                            // Verbindung schließen
}
```

**Sockets: Auswertung**

- Low-Level-Schnittstelle (L4)
- Effizient, aber inkompatibel zu den Protokollen (L5-7) RPC und RMI, daher als Ergänzung
- Problem: Big-Endian / Little-Endian
- Abgrenzung: WebSocket-Protokoll (L5-7)
