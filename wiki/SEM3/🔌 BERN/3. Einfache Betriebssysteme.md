## 3.1 Laden von Programmen

### 3.1.1 Rationalisierung des Ladevorganges

Manuelles Laden über Konsoleneingaben ist **extrem zeitaufwendig und fehleranfällig**.

![[3-robotron-4201-konsole.jpeg]]
*Kleinrechnersystem robotron 4201, ca. 1977 (Quelle: http://www.computermuseum.efb-1.de/) – Hauptspeicherabbild als (Papier-)Tabelle*

Das Hauptspeicherabbild lag nur als Papiertabelle vor (vgl. [[2. Einfache Computer#2.5.2 Speicherbelegungsplan|Speicherbelegungsplan]]). Der Bediener musste jeden Eintrag von Hand über die Konsole eingeben – und das bei jedem Programmstart aufs Neue.

$\rightarrow$ **Forderung:** Der Ladevorgang soll durch Dienstprogramme unterstützt werden, die sich permanent im Hauptspeicher befinden.

### 3.1.2 Maschinenlesbare Hauptspeicherabbilder

Damit ein Programm das Laden übernehmen kann, muss das Hauptspeicherabbild auf einem Datenträger stehen, den der Rechner selbst lesen kann.

**Geeignete Datenträger** – typisch für Computer der 1. und 2. Generation:

- Lochstreifen
- Lochkarte
- Magnetband
- …

**Kodierung**

- spezifisch für Computerarchitektur (Wortbreite, …)
- datenträgerspezifische Darstellung von Adressen und HS-Inhalten
- …

**Einlesen**

- durch Ladeprogramme

**Erzeugung** durch Computer-Software, z. B.

- durch Maschinenkodeübersetzer, sog. Assembler *(wird später behandelt, siehe [[#3.4.5 Assembler]])*
- …

### 3.1.3 Maschinenlesbarer Datenträger: Lochstreifen

Ein Lochstreifen ist geeignet zur Darstellung binärer Informationen („Loch“ oder „kein Loch“).

**Beispiele:**

- 5-Kanal-Lochstreifen für Fernschreibertechnik
- 8-Kanal-Lochstreifen für Datenverarbeitungstechnik
  - Kanäle längs der Bandrichtung
  - Zeichen quer zur Bandrichtung, geeignet zur Darstellung von 8 Bit

![[3-lochstreifen-aufbau.jpeg]]

Jede Querreihe ist also ein **Zeichen**, jede Längsspur ein **Kanal** (= eine Bitstelle). Bei 8 Kanälen passt genau ein Byte in ein Zeichen. Die kleinere **Transportspur** enthält keine Daten, sondern dient dem Weitertransport des Bandes.

**Beispiel Lochstreifentechnik robotron 4201**

![[3-robotron-4201-lochstreifentechnik.jpeg]]

Der Kreislauf auf dem Bild: Die **Dienstprogramme** im Rechner geben ein Programm über den Stanzer aus (**„Stanzen“**). Der Lochstreifen wird **extern zwischengelagert** und kann später über den Lochstreifenleser wieder eingelesen werden (**„Laden“**).

### 3.1.4 (Ur-)Ladeprogramme

Das Hauptspeicherabbild auf externem Datenträger ist **mehrfach verwendbar**.

(Ur-)Lader befinden sich permanent im Speicher und schaffen die Voraussetzung für einen Programmstart.

![[3-urlader.jpeg]]

Der (Ur-)Lader macht also aus dem **Hauptspeicherabbild** auf dem Datenträger die tatsächliche **Hauptspeicherbelegung**.

**Wie kommt der Lader in den Hauptspeicher?**

- manuelle Eingabe eines einfachen Urladers (nur wenige Befehle erforderlich)
- evtl. Nachladen eines leistungsfähigen Laders

**Warum?** Der Lader ist selbst ein Programm und muss irgendwie in den Speicher kommen. Deshalb wird nur ein winziger Urlader von Hand eingegeben – der kann dann einen größeren, leistungsfähigeren Lader vom Datenträger nachladen.

## 3.2 Informationskodierung auf Datenträger Lochband

### 3.2.1 Darstellung von Textzeichen

Darstellung von Textzeichen, z. B. im 7-Bit-[[0. Informatik-Grundbegriffe#0.4 Darstellung von Texten|ASCII-Kode]]:

| Zeichen | ASCII-Kode (hex.dez.) |
|---|---|
| Leerzeichen | 20 |
| … | |
| 0 | 30 |
| 1 | 31 |
| … | |
| A | 41 |
| B | 42 |
| … | |
| a | 61 |
| b | 62 |
| … | |

![[3-lochband-ascii-paritaet.jpeg]]

**Paritätsbits** dienen der Fehlerkontrolle beim Einlesen. Da ASCII nur 7 Bit braucht, bleibt auf dem 8-Kanal-Band ein Kanal frei – dort steht das Paritätsbit (im Bild rot).

**Gerade Parität:** Das Bit wird gesetzt, wenn die Bitanzahl im ASCII-Zeichen ungerade ist, sonst nicht.

Kodiert sind auf dem Band nacheinander: A, B, C, Leerzeichen, A, B, C, Leerzeichen, 1, 2, 3, Leerzeichen, *Ignorieren*, Z, z, +.

**Beispiel:**

- A = $41_{16}$ = 100 0001 → 2 Einsen (gerade) → Paritätsbit **nicht** gesetzt
- C = $43_{16}$ = 100 0011 → 3 Einsen (ungerade) → Paritätsbit **gesetzt**

Mit Paritätsbit hat jedes Zeichen also immer eine **gerade** Anzahl Löcher. Wird beim Einlesen ein Loch falsch erkannt, ist die Anzahl plötzlich ungerade – der Fehler fällt auf.

### 3.2.2 Darstellung von Daten und Maschinenbefehlen

Darstellung von Daten und Maschinenbefehlen, z. B. byteweise in je einem Zeichen.

![[3-lochband-maschinenkode.jpeg]]

- **Befehle:** A1 51 01 01 D0 A3 53 01 …
- **Daten:** 2C 01 64 00 …

Das sind genau die Bytes des Beispielprogramms aus dem [[2. Einfache Computer#2.5.2 Speicherbelegungsplan|Speicherbelegungsplan]] (`MOV AX,[Z1]`, `ADD AX,DX`, `MOV [Z2],AX` sowie die Werte 300 und 100).

> **Merke:** Bei dieser Kodierung fehlen Fehlerkontrollen! Ein Byte belegt alle 8 Kanäle – für ein Paritätsbit ist kein Platz mehr.

### 3.2.3 Darstellung von Hauptspeicheradressen und Blockstruktur

Darstellung von Hauptspeicheradressen, z. B. hexadezimal in mehreren Zeichen (4 Zeichen bei 32-Bit-Rechnern).

Damit im Hauptspeicherabbild nicht für jeden Hauptspeichereintrag Adresse **und** Inhalt kodiert werden müssen, bevorzugt man eine Zusammenfassung von Bytegruppen zu **Blöcken**, deren Inhalte sequentiell ab der Blockanfangsadresse stehen sollen.

Statt jedem Byte seine eigene Adresse mitzugeben, nennt man die Adresse also nur **einmal pro Block** – alle folgenden Inhalte gehören an die direkt anschließenden Speicherstellen.

![[3-lochband-blockstruktur.jpeg]]

Auf dem Band folgen die Blöcke einfach hintereinander: Header, Body, Trailer, Header, Body, Trailer, …

**Blockstruktur**

| Teil | Inhalt |
|---|---|
| Header | Angaben zum Block: Typ, Größe, Adresse, … |
| Body | HS-Inhaltsangaben |
| Trailer | Angaben zum Block: Checksequenzen zur Fehlerkontrolle, … |

### 3.2.4 Beispiel für eine Blockstruktur

Innerhalb eines Blockes gibt es keine Zeichen ohne Bedeutung, außerhalb werden Zeichen mit den Bedeutungen 00H und FFH überlesen.

00H ist ein Zeichen ganz ohne Löcher (leeres Band), FFH eines mit allen Löchern – so wie das Zeichen *Ignorieren* in [[#3.2.1 Darstellung von Textzeichen]]. Zwischen den Blöcken darf das Band also leer oder „überstanzt“ sein.

**Header**

- Blockanfangskennung
- Anzahl der Zeichen im Block, üblicherweise nicht mehr als 64 Zeichen
- Typ des Blockes, wichtig für die evtl. Zuordnung zu Code-, Datensegment, …
- Blockanfangsadressentyp, z. B. absolute Adresse oder relativ zum Segmentanfang
- Blockanfangsadresse

**Body**

- HS-Inhaltsangaben, Anzahl entsprechend der Blocklänge
- Zieladressierung sequentiell ab Blockanfangsadresse

**Trailer**

- Checksequenz gebildet durch Exklusiv-Oder der einzelnen Blockzeicheninhalte

**Warum Exklusiv-Oder?** Das XOR aller Zeichen ändert sich, sobald sich ein einzelnes Bit in einem Zeichen ändert. Der Lader bildet beim Einlesen dasselbe XOR und vergleicht es mit dem Trailer – stimmen beide nicht überein, ist der Block fehlerhaft (siehe [[#3.2.5 Leistungsfähige Lader]]). Damit wird die Fehlerkontrolle nachgeholt, die bei der byteweisen Kodierung fehlt.

### 3.2.5 Leistungsfähige Lader

Mit der Blockstruktur kann ein Lader deutlich mehr, als nur Bytes in den Speicher zu kopieren. Leistungsfähige Lader müssen in der Lage sein,

- die Lage der Segmente im Hauptspeicher zu bestimmen,
  - entweder selbständig
  - oder nach Vorgaben,
- blockweise den Maschinenkode eines Programmes einzulesen
  - und dabei die Checksequenz des Blockes zu bilden
  - und diese mit der Checksequenz im Blocktrailer zu vergleichen.
- Im positiven Fall muss die zugehörige Speicherbelegung realisiert werden.
- Im negativen Fall muss der Ladevorgang mit einer Fehleranzeige abgebrochen werden.

## 3.3 Systemroutinen und Programmsteuerung

### 3.3.1 Routineprobleme

*Warum soll jeder Programmierer alles neu entwickeln?*

Fast jedes Programm muss z. B. Zeichen von der Tastatur lesen oder auf den Drucker ausgeben. Statt dass jeder Programmierer diese Routinen selbst schreibt, stellt man sie einmal zentral im Hauptspeicher bereit.

**Hauptspeicherresidente Systemroutinen**

- Nutzung der peripheren Geräte
- …

(Gefahr: Systemroutinen können durch fehlerhafte Programme überschrieben werden)

**Hauptspeicheraufteilung**

| Ladeprogramm, Systemroutinen (resident) | Systemroutinen (transient) | Anwenderprogramm |
|---|---|---|

- **resident:** ständig im Hauptspeicher
- **transient:** werden nur bei Bedarf geladen und können danach wieder überschrieben werden

### 3.3.2 API – Anwenderprogrammierschnittstelle

#### 3.3.2.1 Ein- und Ausgabefunktionen

Die API ist die Schnittstelle, über die ein Anwenderprogramm die Systemroutinen aufruft.

Ein- und Ausgabefunktionen für die wichtigsten E/A-Geräte:

| Gerät | Funktion |
|---|---|
| Tastatur | einfache Eingabe von Zeichen, Umwandlung in ASCII-Kode |
| Bildschirm | Ausgabe von Zeichen im ASCII-Kode, Bildschirmrollen |
| Systemeingabe und Systemausgabe | |

Anwenderprogramme sollen einfach (ohne HW-Kenntnisse) Daten einlesen und ausgeben können.

**Z. B.:** Statistikprogramm will aktuelle Daten über Lochstreifen lesen, verarbeiten und in Listenform auf dem Drucker ausgeben.

#### 3.3.2.2 Beispiel: PC-BIOS „Zeichenübernahme von Tastatur“

**Entlastung Anwendungsprogrammierer**

- Test Tastaturtyp
- Zuordnung der Zeichen zu Tasten (nationale Besonderheiten)
- Stellung der Umschalttasten wegen Mehrfachbelegung von Tasten
- Feststellen Tastaturprellen

**Maschinenkode-API**

```asm
MOV AH,0      ;Funktionsangabe fuer BIOS im Reg. AH
INT 16H       ;Aufruf BIOS-Routine
```

**BIOS** prüft dann, ob eine Tastaturbetätigung vorliegt, und übergibt ggf. den ASCII-Zeichenkode im Register AL.

Das Anwenderprogramm muss also nur zwei Befehle kennen: In AH legt es fest, *welche* BIOS-Funktion es möchte, mit `INT 16H` ruft es die Routine auf. Alle Details aus der Liste oben erledigt das BIOS.

### 3.3.3 Steuerfunktionen

**Probleme**

- hoher Bedienaufwand
- Endlosschleifen in fehlerhaften Programmen
- irregulärer Programmlauf, z. B. unzulässige Hauptspeicherzugriffe
- irreguläres Programmende, z. B. „Division durch Null“

**Lösung**

- Steuerung/Überwachung des Laufes der Anwendungsprogramme

Ohne eine solche Überwachung legt z. B. eine Endlosschleife den ganzen Rechner lahm, bis der Bediener von Hand eingreift.

In einfachen Betriebssystemen, z. B. MS-DOS, nur ansatzweise; ab Computern der 3. Generation voll verwirklicht.

### 3.3.4 Stapelverarbeitung

**Ziele:**

- automatisierte Auftragsbearbeitung
- Maximierung Auftragsdurchsatz

**Job** (Nutzerauftrag, betriebssystemspezifisch): Jobs ursprünglich überwiegend in Lochkartenform; wurden hintereinander in Lochkartenleser gelegt (gestapelt).

**Steueranweisungen**

| Steueranweisung | Inhalt |
|---|---|
| Jobkopf | Jobidentifikation, Abrechnungsinformationen |
| Jobschritt | Anforderung zum Programmaufruf, ggf. Daten bzw. Datenreferenzen |
| … u. U. weitere Jobschritte | |
| Jobende | |

![[3-stapelverarbeitung.jpeg]]

Ein **Steuerprogramm** arbeitet den Jobstapel ab:

1. Initialisierung
2. **Zyklus:** Lesen Steueranweisung (von der Systemeingabe, also aus dem Jobstapel)
3. Laden Programm
4. Aufruf des Anwenderprogramms
5. Rücksprung ins Steuerprogramm
6. Zyklus fortsetzen

### 3.3.5 Dialogverarbeitung

![[3-dialogverarbeitung.jpeg]]

Der Ablauf ist derselbe Zyklus wie bei der [[#3.3.4 Stapelverarbeitung|Stapelverarbeitung]]. Der Unterschied: Die Steueranweisung bzw. das **Kommando** kommt nicht aus einem vorbereiteten Jobstapel, sondern wird von einem Nutzer am **Terminal** eingegeben.

### 3.3.6 Zugriffsrechte, Privilegien

Weil Systemroutinen und sogar der Lader durch fehlerhafte Anwenderprogramme überschrieben werden können (siehe [[#3.3.1 Routineprobleme]]), muss der Speicher geschützt werden.

**Forderung**

- Reduktion des Hauptspeicherzugriffsrechtes für Anwenderprogramme
- Privilegierung der Systemroutinen

**Hauptspeicheraufteilung**

![[3-hauptspeicheraufteilung-zugriff.jpeg]]

- Steuerprogramm, Ladeprogramm, Systemroutinen (resident und transient): uneingeschränkter **Zugriff** erforderlich
- gesteuertes Anwenderprogramm: möglichst **Zugriff nur auf eigenen Speicherbereich**

## 3.4 Dienstleistungsprogramme

### 3.4.1 Dienstleistungsprogramme

Neben Lader und Systemroutinen braucht der Rechnerbetrieb weitere Hilfsprogramme. Sie gehören nicht zum Kern des Betriebssystems, werden aber meist mit ihm ausgeliefert.

Spezielle Anwendungsprogramme zur Unterstützung des Rechnerbetriebes:

- Hardwaretestprogramme
- Programme zur Wartung und Pflege von Datenträgern
- Programme zur Datenverwaltung
- Programmierunterstützungen

Eine exakte Abgrenzung zwischen Dienstleistungsprogrammen und reinen Anwendungsprogrammen ist nicht möglich, z. B.:

| Programm | Einordnung |
|---|---|
| Windows „Arbeitsplatz“ | Dienstleistungsprogramm |
| Windows „Editor“ | Dienstleistungsprogramm? |

### 3.4.2 Unterstützung Systemanlauf

**Systemanlaufroutine**

- Laden der benötigten residenten Teile des Betriebssystems
- Initialisierung von Hardwarekomponenten,
  - z. B. Test der Konfiguration, Herstellen der Arbeitsbereitschaft …
- Initialisierung von Softwarekomponenten,
  - z. B. definierte Belegung der Arbeitsdaten

### 3.4.3 Editoren, Übersetzer und Verbinder

![[3-editor-assembler-verbinder.jpeg]]

Der Weg vom Programmierer zum lauffähigen Programm:

1. Mit dem **Editor** wird der **Quellkode** geschrieben.
2. Der **Assembler** übersetzt ihn in **Objektkode**.
3. Der **Verbinder** fügt den Objektkode – ggf. zusammen mit weiteren Objektkode-Modulen – zum fertigen **Maschinenkode** zusammen.

**Henne-/Ei-Problem:** Wie entwickelt man

- Editor,
- Assembler,
- Verbinder?

Das Problem: Um einen Editor zu schreiben, bräuchte man bereits einen Editor – und um einen Assembler zu übersetzen, bereits einen Assembler.

$\rightarrow$ wird später erläutert (siehe [[#3.4.7 Wie wurden die Dienstleistungsprogramme entwickelt?]])

### 3.4.4 Arbeitsgänge bei Entwicklung eines Programmes

**Voraussetzung:** Lader resident im Hauptspeicher

| Start | Aufgabe |
|---|---|
| Lader | Laden Editor |
| Editor | Texteingabe/Ausgabe maschinenlesbarer Quellkode |
| Lader | Laden Übersetzer |
| Übersetzer | Eingabe Quellkode / Ausgabe Objektkode |
| Lader | Laden Verbinder |
| Verbinder | Umwandlung Objektkode (evtl. mehrere Moduln) in ein Anwender-Maschinenkodeprogramm |
| Lader | Laden Anwenderprogramm |
| Anwender-Programm | programmierte Aufgabe, evtl. fehlerhafte Ausführung **(Gefahr: Lader kann überschrieben werden!)** |

Nur der Lader bleibt ständig im Speicher. Alle anderen Werkzeuge werden nacheinander geladen, erledigen ihre Aufgabe und machen dann Platz für das nächste. Deshalb steht zwischen je zwei Arbeitsschritten wieder der Lader.

### 3.4.5 Assembler

Spezielles Übersetzerprogramm (vgl. [[0. Informatik-Grundbegriffe#0.6.2.2 Zweite Generation: Assemblersprachen|Assemblersprachen]] in TGI):

- **maschinennah**, jeder Maschinenbefehl kann in Assembler beschrieben werden
  - $\rightarrow$ Ausnutzung aller Fähigkeiten des Computersystems
  - $\rightarrow$ Programme sind nur auf Computern einer Architekturfamilie lauffähig.
- **Vorteile gegenüber reiner Maschinensprache**
  - Symbolische Bezeichnung der Maschinenbefehle
  - Symbolische Adressierung von Befehlen und Daten
  - Kommentierung des Programminhaltes im Programm möglich

Nachfolgend ein Assemblerprogramm-Beispiel für die Ausgabe von „Hallo Welt“ auf einem Rechner mit x86-Intelprozessor und Betriebssystem MS-DOS (Quelle: www.wikipedia.org):

```asm
ASSUME  CS:CODE, DS:DATA        ;- Assembler die Zuordnung der Segmentregister zu den Segmenten mitteilen

DATA    SEGMENT                 ;Beginn des Datensegments
Meldung: db "Hallo Welt"        ;- Zeichenkette "Hallo Welt"
nl:     db 13, 10               ;- Neue Zeile
        db "$"                  ;- Zeichenkettenende-Kennzeichen
DATA    ENDS                    ;Ende des Datensegments

CODE    SEGMENT                 ;Beginn des Codesegments
Anfang: mov ax, DATA            ;- Adresse des Datensegments in das Register "AX" laden
        mov ds, ax              ; In das Segmentregister "DS" uebertragen
        mov dx, OFFSET Meldung  ;- Offsetadresse (zum Datensegment) für Textvariable
BS1:    mov ah, 09h             ;- die Unterfunktion 9 "Textausgabe" des MS-DOS-Betriebssystems
        int 21h                 ;- MS-DOS-Dienstaufruf
        mov ax, 4C00h           ;- die Unterfunktion 4Ch (Programmbeendigung) festlegen
        int 21h                 ;- MS-DOS-Betriebssystemaufruf
CODE    ENDS                    ;Ende des Codesegments

END     Anfang                  ;- Festlegen der Programm-Einsprungsadresse
```

Das Programm nutzt die API von MS-DOS genauso wie das Tastaturbeispiel die BIOS-API (siehe [[#3.3.2.2 Beispiel: PC-BIOS „Zeichenübernahme von Tastatur“]]): In AH wird die gewünschte Funktion festgelegt (09h = Textausgabe, 4Ch = Programmbeendigung), `int 21h` ruft das Betriebssystem auf. Das `"$"` markiert für die Textausgabe das Ende der Zeichenkette.

### 3.4.6 Wie arbeitet ein Assembler?

Normalerweise werden **zwei** sequentielle **Durchläufe** des Quellprogramms durchgeführt.

**Warum zwei?** Ein Befehl kann eine Marke verwenden, die erst weiter unten im Programm definiert wird. Beim ersten Lesen ist deren Adresse noch unbekannt. Deshalb sammelt der erste Durchlauf nur alle Adressen, erst der zweite erzeugt den Maschinenkode.

#### 3.4.6.1 Aufstellung der Zuordnungstabelle

Zuordnungstabelle der symbolischen Adressen (Marken) zu den HS-Adressen:

| Segment | Marke | Offsetadresse |
|---|---|---|
| DATA | Meldung | 00 00 H |
| DATA | nl | 00 0A H |
| … | … | … |
| CODE | Anfang | 00 00 H |
| CODE | BS1 | 00 08 H |
| … | … | … |

- In jedem Segment beginnt der Adresszähler mit 0.
- Befindet sich in der Zeile eine Marke, wird dieser der Wert des Adresszählers zugeordnet.
- Danach wird Zeile für Zeile geprüft, wie viel Speicherplatz die Anweisung belegt, und der Adresszähler entsprechend erhöht.

**Nachgerechnet am Beispiel:**

- `Meldung` steht am Anfang des Datensegments → 00 00 H. "Hallo Welt" belegt 10 Byte, also beginnt `nl` bei $10 = 0\text{A}_{16}$ → 00 0A H.
- `Anfang` steht am Anfang des Kodesegments → 00 00 H. Die drei Befehle davor (`mov ax, DATA`, `mov ds, ax`, `mov dx, OFFSET Meldung`) belegen zusammen 8 Byte, also liegt `BS1` bei 00 08 H.

#### 3.4.6.2 Berechnung und Ausgabe des Hauptspeicherabbilds des Programmes

Für das Datensegment werden Zeile für Zeile die definierten Daten kodiert. Wenn genügend Daten kodiert wurden, wird ein Maschinenkodeblock ausgegeben, so lange bis das Segmentende erreicht ist.

Für das Kodesegment werden ebenfalls Zeile für Zeile die symbolischen Befehlskodes in Maschinenkode umgewandelt. In den Adressteil der Befehle werden anstelle der symbolischen Adressen die (Offset-)Adressen aus der Zuordnungstabelle eingesetzt. Wenn genügend Daten kodiert wurden, wird ein Maschinenkodeblock ausgegeben, so lange bis das Segmentende erreicht ist.

Im Ergebnis liegt der Maschinenkode des Programms komplett auf einem externen Datenträger vor und kann beliebig oft genutzt werden.

### 3.4.7 Wie wurden die Dienstleistungsprogramme entwickelt?

**1945 bis 1955**

- Schritt für Schritt wurden Lader, Assembler, Editoren entwickelt $\rightarrow$ extrem mühsame Arbeit
- Auf dieser Basis konnten in Assemblersprache weitere Systemunterstützungen programmiert werden, z. B. die ersten Compiler für problemorientierte Programmiersprachen FORTRAN, …

**Danach**

- Entwicklung von Assemblern auf (älteren) Rechnern für nächste Rechnerarchitekturen (**Cross-Software**)

Damit löst sich das [[#3.4.3 Editoren, Übersetzer und Verbinder|Henne-/Ei-Problem]]: Die ersten Werkzeuge wurden mühsam direkt in Maschinenkode erstellt. Jedes fertige Werkzeug erleichterte dann die Entwicklung des nächsten. Für neue Rechner musste man nicht wieder bei null anfangen, sondern konnte die Software auf einem vorhandenen Rechner erzeugen.

## 3.5 Einfache Betriebssysteme in der Praxis

### 3.5.1 CP/M (Control Program for Microcomputers)

Dominantes Betriebssystem für 8-Bit-Mikrorechner (I8080, Zilog 80), 1974 Digital Research Inc.

![[3-cpm-schichten.jpeg]]

- **CCP** (Console Command Prozessor): Dialog-Steuersystem
- **BDOS** (Basic Disk Operating System): Dateiverwaltung (Disketten)
- **BIOS** (Basic Input/Output System): Hardware-Abstraktionsschicht, einheitliche Nutzer-API; geliefert vom Hersteller

Das Bild zeigt den Schichtenaufbau: Die **Application** ruft Dienste von CCP, BDOS oder BIOS auf (**Call**) und erhält das Ergebnis zurück (**Return**). Der CCP startet die Anwendung (**Start**) und bekommt die Kontrolle zurück, wenn sie endet (**Exit**).

**Warum liefert der Hersteller das BIOS?** Nur das BIOS hängt von der konkreten Hardware ab. CCP und BDOS bleiben auf allen Rechnern gleich – so lief CP/M auf Mikrorechnern vieler verschiedener Hersteller.

### 3.5.2 MS-DOS (Microsoft Disk Operating System)

Dominantes Betriebssystem für 16-Bit-Mikrorechner (I8086), 1980 Microsoft.

Ähnliche Struktur wie CP/M:

| CP/M | MS-DOS (nach Laden von MS-DOS) |
|---|---|
| BIOS liefert Hersteller | IO.SYS |
| BDOS entspricht | MSDOS.SYS |
| CCP entspricht | COMMAND.COM |

**Hauptverbesserung:** Dateisystem FAT (File Allocation Table) mit Baumstruktur, geeignet für Festplatten

MS-DOS setzte sich durch, weil es von IBM für seine IBM-PC lizenziert wurde.

### 3.5.3 Historie

Dominanz einfacher Betriebssysteme:

Die Zeitleiste reicht von 1950 bis 2020. Einfache Betriebssysteme dominierten nacheinander bei **Großrechnern**, dann bei **Mikrorechnern** und heute bei **Mikrokontrollern** (gestrichelter Pfeil bis in die Gegenwart).

### 3.5.4 BIOS – Trend zum einfachen Betriebssystem

Moderne Rechner werden meist nicht als blanke Hardware verkauft, sondern verfügen ab Werk über eine Firmware (BIOS) in einem nichtflüchtigen Speicher (EPROM, Flash) mit folgenden Aufgaben:

| Aufgabe | Beschreibung |
|---|---|
| Bootstrapping | Einlesen von sog. Images von Betriebssystemen |
| HAL | Hardware Abstraction Layer $\rightarrow$ allgemeine Schnittstelle zum Ansteuern der Computerhardware während des Systemstarts |
| Bedienerschnittstelle | |

Das BIOS kann als einfaches Betriebssystem bezeichnet werden.

**Merke:** Das Bootstrapping des BIOS ist der moderne Nachfolger des [[#3.1.4 (Ur-)Ladeprogramme|Urladers]] – nur dass er heute ab Werk im nichtflüchtigen Speicher steckt, statt von Hand eingegeben zu werden.

## Review & Learning
> [!summary] Zusammenfassung
> Einfache Betriebssysteme entstanden aus dem Wunsch, die Routinearbeit am „nackten“ Computer zu automatisieren. Zuerst wurde das Laden rationalisiert: Hauptspeicherabbilder wurden auf maschinenlesbaren Datenträgern (Lochstreifen, Lochkarte, Magnetband) gespeichert und von residenten (Ur-)Ladern eingelesen. Auf dem Lochband werden Textzeichen (ASCII mit Paritätsbit), Maschinenkode und Adressen kodiert; eine Blockstruktur aus Header, Body und Trailer (Checksequenz per Exklusiv-Oder) spart Adressangaben und ermöglicht Fehlerkontrolle durch leistungsfähige Lader. Hauptspeicherresidente Systemroutinen stellen über eine API (z. B. PC-BIOS `INT 16H`) Ein-/Ausgabefunktionen bereit. Steuerfunktionen überwachen Anwendungsprogramme; Stapelverarbeitung (Jobs mit Steueranweisungen) und Dialogverarbeitung werden von einem Steuerprogramm in einem Zyklus abgearbeitet. Zugriffsrechte schützen Systemroutinen vor Anwenderprogrammen. Dienstleistungsprogramme wie Editor, Assembler (zwei Durchläufe: Zuordnungstabelle, dann Maschinenkode) und Verbinder unterstützen die Programmentwicklung. Praxisbeispiele sind CP/M (CCP, BDOS, BIOS) und das daraus abgeleitete MS-DOS mit FAT-Dateisystem; das heutige BIOS gilt selbst als einfaches Betriebssystem.
